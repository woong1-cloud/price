# 멀티 브랜드 확산 — 범용성 진단 & 확장 설계

> **질문**: 이 대시보드를 SPAO 외 다른 브랜드로 확산할 수 있는가? 일부 커스텀이 필요한 영역은?
> **결론(요약)**: **가능하다.** 구조(업로드→파싱→집계→화면→주차 누적·WoW)는 **100% 브랜드 무관**이고, 브랜드 종속 부분은 **단 4개 파일의 "데이터/설정"** 에 격리돼 있다. 이를 **브랜드 설정(Brand Config) 레이어**로 분리하면 *"새 브랜드 = 코드 재작성이 아니라 설정값 채우기"* 가 된다.

---

## 1. 범용성 진단 — 무엇이 공용이고 무엇이 브랜드 종속인가

### ✅ 그대로 재사용 (브랜드 무관, 전체의 ~85%)
| 영역 | 위치 | 비고 |
|---|---|---|
| 업로드→자동인식→파싱 파이프라인 | `parseExcel.js` 골격 | 헤더 키워드 기반이라 컬럼명만 같으면 동작 |
| 주차 누적·WoW 비교 모델 | `weekKey.js`, `weekNav.js`, `storage.js` | 완전 범용 |
| 클라우드 저장·gzip 압축 | `storage.js`, `supabase/schema.sql` | 완전 범용 |
| KPI·전환·퍼널·재입고 계산 로직 | `metrics.js` 핵심 | 산식은 브랜드 무관 |
| 화면(L1~L4) 컴포넌트 | `components/*.jsx` | 라벨/색만 설정화하면 범용 |
| 데이터셋 10종 스키마 | `API_REQUIREMENTS.md` | **핵심 통찰 ↓** |

> **🔑 핵심 통찰**: 데이터셋 10종은 **이랜드 공통 EC 백오피스(BO)의 표준 추출 형식**이다. 따라서 **같은 BO를 쓰는 자매 브랜드(미쏘·후아유·뉴발란스키즈·로엠 등)는 동일한 엑셀 형식**을 내려받을 가능성이 높다 → **파서를 거의 그대로 재사용** 가능. (브랜드별 BO 추출 형식이 다르면 헤더 동의어만 추가)

### 🛠 브랜드별 커스텀 필요 (격리된 4개 파일 + 브랜딩)
| # | 종속 항목 | 위치 | 왜 브랜드마다 다른가 |
|---|---|---|---|
| 1 | **스타일코드 규칙** | `styleCodeParser.js` — 브랜드 접두사(`SP`), `ITEM_CODE_TABLE`, `GENDER_CODE_TABLE`, 자릿수(`slice(2,4)`/`[4]`/`[7]`) | 브랜드마다 품번 체계가 다름 |
| 2 | **IP/콜라보 · 카테고리 사전** | `categorize.js` — `IP_MAP`, 제외목록, `getCategory` 키워드 | 콜라보 IP·카테고리 구성이 브랜드별 상이(콜라보 없는 브랜드도 있음) |
| 3 | **매장 구역 분류** | `metrics.js` — `EXPLORE_GROUPS`/`PURCHASE_GROUPS`/`TOP_GROUPS`, `기획전매장` 등 | 자사몰 사이트 구조(매장그룹 명칭)가 브랜드별 다름 |
| 4 | **매장명 접두사 · 매체·임계값** | `parseExcel.js`(`'스파오공홈_P_'`), `metrics.js`/컴포넌트(이탈률 38·취소율 8 등), `MEDIA_COLORS` | 브랜드별 접두사·기준·매체 구성 차이 |
| 5 | **브랜딩/식별** | `App.jsx`·`PasswordGate.jsx` 타이틀, 색, 도메인, 비밀번호, 저장키(`spao_v3_*`), Supabase 프로젝트 | 브랜드 아이덴티티·접속·데이터 격리 |

> 종속 지점이 **아키텍처가 아니라 전부 "데이터/설정값"** 이라는 점이 핵심이다. 즉 **분리만 하면 범용 플랫폼**이 된다.

## 2. 권장 설계 — "Brand Config" 레이어로 분리

브랜드 종속값을 **단일 설정 객체**로 모으고, 코드는 그 설정을 읽게 바꾼다.

```
src/brands/
  ├─ index.js            ← 현재 활성 브랜드 선택(환경변수 VITE_BRAND 로)
  ├─ spao.js             ← SPAO 설정 (지금 하드코딩된 값들을 이쪽으로)
  ├─ mixxo.js            ← 신규 브랜드 예시
  └─ _schema.md          ← 설정 항목 정의
```

### Brand Config 객체 스펙(예시)
```js
export default {
  id: 'spao',
  name: 'SPAO 자사몰',
  shortName: 'SPAO',
  theme: { primary: '#378ADD', /* 보조색… */ },
  auth: { storageKey: 'spao_v3_auth' },           // 브랜드별 분리
  supabase: { /* URL·anon키는 env로 */ },

  // 1) 스타일코드 규칙
  styleCode: {
    brandPrefix: 'SP', brandName: 'SPAO',
    positions: { item: [2,4], year: 4, gender: 7 },
    itemTable:   { /* TC: '코튼 팬츠', … */ },
    genderTable: { G:'여성', W:'여성', M:'남성', C:'공용', K:'키즈', U:'콜라보' },
    newYearCode: 'G',
  },

  // 2) IP/카테고리
  ipMap: [ ['lucy','LUCY'], /* … */ ],
  ipExclude: { materials:[…], contains:[…] },
  categoryKeywords: { /* … */ },

  // 3) 매장 구역 분류
  store: {
    exploreGroups: ['홈매장','공통매장'],
    purchaseGroups: ['검색매장','카테고리매장','기획전매장','유닛매장','상품상세매장'],
    topGroups: ['검색매장','카테고리매장','기획전매장'],
    namePrefix: '스파오공홈_P_',
  },

  // 4) 매체·임계값
  media: { order: ['MOBILE','APP','PC'], colors: { MOBILE:'#378ADD', APP:'#5DCAA5', PC:'#B4B2A9' } },
  thresholds: { bounceRate: 38, cancelRate: 8, cartConvLow: 5 },

  // 5) 파서 헤더 동의어(브랜드 BO가 다를 때만 보강)
  headerAliases: { /* 선택 */ },
}
```

### 적용 방식
- `styleCodeParser.js` / `categorize.js` / `metrics.js` / 컴포넌트가 **하드코딩 대신 활성 브랜드 설정을 참조**하도록 변경.
- 활성 브랜드는 빌드 환경변수 `VITE_BRAND=spao` 로 선택.
- **새 브랜드 추가 = `src/brands/<brand>.js` 한 개 작성 + 빌드.** 코어 코드 무수정.

## 3. 멀티테넌시(데이터 격리) 3안

| 안 | 방식 | 장점 | 단점 | 추천 |
|---|---|---|---|---|
| **A. 브랜드별 독립 배포** | 브랜드마다 별도 빌드(`VITE_BRAND`) + **별도 Supabase 프로젝트** + 별도 도메인 | 데이터·권한 완전 격리, 가장 단순·안전, 장애 전파 없음 | 운영 인스턴스 N개 | ⭐ **단기 추천** |
| **B. 단일 앱 + brand 컬럼** | 한 배포에서 `weekly_snapshots`에 `brand` 컬럼 추가 + 헤더에 브랜드 선택기 | 한 곳에서 다 봄(본사 통합 뷰 용이) | RLS·권한 설계 필요, 데이터 섞임 위험 | 중기(본사 통합 대시 필요 시) |
| **C. 스키마/DB 분리 + 통합 포털** | 브랜드별 스키마 + 상위 포털 | 격리 + 통합 동시 | 구축 비용 큼 | 장기 |

> **권장**: 시작은 **A(브랜드별 독립 배포)** — Brand Config만 갈아끼우면 즉시 새 브랜드 인스턴스가 뜬다. 본사가 "전 브랜드 한눈에"를 원하면 **B**로 확장.

## 4. 신규 브랜드 온보딩 체크리스트 (브랜드 추가 시 채울 것)

- [ ] **BO 추출 형식 확인**: 데이터셋 10종 헤더가 SPAO와 동일한가? 다르면 `headerAliases` 보강.
- [ ] **스타일코드 규칙**: 접두사, 자릿수(품목/연도/성별 위치), 품목코드표, 성별코드표.
- [ ] **콜라보 유무 / IP 목록**: 있으면 `ipMap`, 없으면 콜라보 분류 비활성.
- [ ] **자사몰 매장 구역 명칭**: 탐색/구매 그룹, 매장명 접두사.
- [ ] **매체 구성**: APP 유무 등.
- [ ] **임계값**: 이탈률·취소율 등 브랜드 기준.
- [ ] **브랜딩**: 이름·로고·테마색·도메인.
- [ ] **접속/격리**: 비밀번호, Supabase 프로젝트(또는 brand 키), 환경변수.
- [ ] **검증**: 1개 주차를 수기 업로드 → 자동 결과와 KPI 일치 확인.

> 이 체크리스트가 곧 "브랜드 설정 파일 1개"의 내용이다.

## 5. 단계별 추진(Phase)

1. **Phase 1 — 설정 추출(리팩터)**: 하드코딩된 SPAO 값을 `src/brands/spao.js`로 이동, 코어가 설정을 읽도록 변경. **기능·화면 동일(회귀 없음)** 이 성공 기준. 테스트(`*.test.js`)로 보증.
2. **Phase 2 — 2번째 브랜드 PoC**: 자매 브랜드 1개 설정 작성 → 독립 배포(A안) → 데이터 검증.
3. **Phase 3 — 온보딩 키트화**: 설정 템플릿 + 본 체크리스트 + 자동 검증 스크립트로 "반나절 온보딩".
4. **Phase 4(선택) — 통합 뷰**: 본사용 멀티브랜드 합본(B안) + 권한.

## 6. 리스크 & 주의

- **스타일코드 체계 상이**: 가장 큰 변수. 브랜드별 품번 규칙을 초기에 확보해야 함(자릿수/코드표).
- **BO 추출 형식 차이**: 컬럼명이 다르면 `detectFileKey`/파서 동의어 보강 필요(아키텍처 변경 아님).
- **콜라보/카테고리 부재 브랜드**: 해당 섹션을 설정으로 끄는 분기 필요(빈 데이터 graceful 처리는 이미 대부분 됨).
- **데이터 격리**: 멀티테넌시 A안이면 자연 격리. B안은 RLS·권한 설계 필수(브랜드 간 열람 차단).
- **회귀 방지**: 설정 추출 시 SPAO 결과가 **바뀌지 않아야** 한다 → 리팩터 전후 스냅샷 비교 테스트 권장.

## 7. 최종 판정

| 항목 | 판정 |
|---|---|
| 다른 브랜드 사용 가능성 | **가능 (높음)** |
| 코어 아키텍처 재사용률 | **~85% 그대로** |
| 브랜드 종속 범위 | **4개 파일 + 브랜딩, 전부 "설정값"** |
| 권장 접근 | **Brand Config 레이어 추출 → 브랜드별 독립 배포(A)** |
| 신규 브랜드 비용 | **설정 파일 1개 작성 + 검증** (코어 무수정) |

> 즉, 지금은 "SPAO 전용 앱"이지만 **설정 분리(Phase 1) 한 번**이면 **브랜드 무관 플랫폼**이 된다. 이 리팩터는 기능 변화가 없어 리스크가 낮고, 이후 브랜드 확산 속도를 크게 높인다.
