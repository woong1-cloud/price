## 0. 요청 요약 (TL;DR)

1. **현재**: 매주 사람이 엑셀 10종을 대시보드에 수기 업로드 → Supabase 저장.
2. **요청**: BO가 **순수 일별 표준 파일(주차 정보 불필요)을 매일 Supabase Storage에 드롭** → 우리 Edge Function이 날짜로 주차를 묶어 검증·적재. **대시보드는 변경 없음.**
3. **핵심 결론**: 주간→일단위로 바꿔도 **데이터 필드 스키마는 불변**(적재 단위/키만 변경). 컴포넌트·집계 로직은 거의 무변경.
4. **저장/보안**: Supabase 유지. 대시보드는 이미 **실제 로그인(Supabase Auth) + RLS(로그인 사용자만)** 으로 보호. 적재는 **서버(Edge Function)의 service_role**로만 수행.
5. **2단계(추후)**: 멀티브랜드 — 브랜드 식별/격리 추가, 대용량·폐쇄망 시 S3 하이브리드.

# Phase 1 — SPAO 대시보드 데이터 자동화

## 1-1. 현재 구조 (As-Is)
```
BO 엑셀 10종 → (사람) 수기 업로드 → 대시보드 파싱 → Supabase weekly_snapshots(주 1행, gzip jsonb) → 화면
```

## 1-2. 목표 (To-Be)
```
BO → (자동, 일배치) 표준 파일 드롭 → Supabase Storage → Edge Function(검증·적재) → weekly_snapshots → 화면(무변경)
```

## 1-3. 구조 검토 — 주간→일단위, 스키마 바뀌나? → **아니오**
| 구분 | 변경 |
|---|---|
| 데이터셋 필드 스키마(1-7) · 날짜 컬럼 · 대시보드 읽기 payload | **변경 없음** |
| 적재 단위/키(주→일 누적) · 멱등 규칙 | 변경 O |
> 컴포넌트는 items만 받아 비율을 재계산하고, 여러 주/일을 합치는 로직(mergePayloads)도 이미 구현됨 → **적재·저장층 작업이지 대시보드 재작성 아님.**

## 1-4. 전송 방식 결정 = **파일 드롭** (Redash 아님)
- Redash는 **조회 도구**일 뿐 데이터를 밀어주는 수단이 아님 → 데이터 공급 경로로 부적합.
- **파일 드롭이 보안상 유리**: BO는 "한 곳에 파일 업로드"만 가능(우리 DB 자격 미보유, 단방향, 감사·재처리 용이).

## 1-5. 적재 인프라 = **Supabase Storage 단독** (권장) / S3는 확장 옵션
- 드롭 위치를 **Supabase Storage(내장 파일 저장소)** 로 하면 **AWS 없이** 한 시스템에서 끝. 추가 비용 0(Pro 플랜 내 포함).
- **S3가 필요해지는 경우**: 폐쇄망 **사설연결(PrivateLink)**·**관리형 SFTP(Transfer Family)**·대용량 원천 보관. 이때만 S3 하이브리드(S3 랜딩 → ETL → Supabase 서빙).
- 구조가 동일해 **버킷만 교체**로 전환 가능.

## 1-6. 파일 드롭 파이프라인 & 사내망 갈림길
```
[BO 사내망] → (HTTPS 업로드) → [Supabase Storage: incoming/] → (트리거/cron)
   → [Edge Function: 표준 스키마 변환·검증] → (service_role) → [weekly_snapshots upsert]
   → 성공: processed/ 이동 / 실패: error/ + 알림
[대시보드] ← 변경 없음
```
**사내망 핵심 질문 = "BO가 아웃바운드 HTTPS 가능한가?"**
- 가능 → 클라우드 버킷에 **직접 업로드**(가장 단순·안전).
- 폐쇄망(아웃바운드 차단) → 사내 스테이징+릴레이 또는 **S3 + PrivateLink/SFTP** 필요.

## 1-7. ★ 데이터 스키마 (10종 — 본문 포함)
**규칙**: 필드명·타입 정확히 일치. `M`=필수, `O`=선택. 금액=원(정수), 비율=number(%), 날짜=`YYYY-MM-DD`(KST), 매체=`MOBILE/APP/PC`.
각 데이터셋 = `items`(상세 행) + 일부 `sigma`(합계). `sigma`는 `items` 합과 일치해야 함.

### ① sales — 주간 판매(상품×일자)
`date`(M) · `media`(M) · `styleCode`(M) · `name`(M) · `qty`(M,int) · `realAmt`(M,원·0이하 제외) · `pv`(O,int)
sigma(M): `{ qty, realAmt, pv }`

### ② cart — 장바구니
`media`(M) · `styleCode`(M) · `name`(M) · `memberType`(O) · `cartCnt`(M) · `orderCnt`(M) · `realAmt`(M,원) · `memberCartCnt`(O) · `nonMemberCartCnt`(O)
sigma(M): `{ cartCnt, orderCnt, realAmt, memberCartCnt, nonMemberCartCnt }`

### ③ wishlist — 관심상품(찜)
`media`(O) · `styleCode`(M) · `name`(M) · `wishCnt`(M) · `orderCnt`(O) · `realAmt`(O,원)
sigma(M): `{ wishCnt, orderCnt, realAmt }`

### ④ customer — 고객 분석(성별×연령)
`gender`(M) · `ageGroup`(M) · `memberType`(O) · `custCnt`(M,구매고객수) · `orderCnt`(O) · `realAmt`(M,원) · `firstBuyCnt`(O,신규)
sigma(M): `{ orderCnt, realAmt, custCnt, firstBuyCnt }`

### ⑤ salesByDate — 기간별 매출분석(일자×매체, 혜택/취소 포함)
`date`(M) · `media`(M) · `buyerCnt`(M) · `orderCnt`(M) · `orderAmt`(M,원) · `realOrderCnt`(M) · `realAmt`(M,원) · `cancelAmt`(M,원) · `discountAmt`(M,원) · `totalBenefit`(M,원)
sigma(M): `{ buyerCnt, orderCnt, orderAmt, realOrderCnt, realAmt, cancelAmt, totalBenefit, discountAmt, pointAmt, shippingFee }`
⚠️ L1 핵심 KPI(취소율·AOV·혜택율)가 sigma 직접 사용 → 합계 정확도 필수.

### ⑥ visit — 방문실적(일자×매체)
`date`(M) · `media`(M) · `uv`(M) · `session`(M) · `pv`(M) · `bounceRate`(M,%) — `media='전체'` 행 제외, sigma 없음

### ⑦ store — 매장 종합(일자×매체×매장)
`date`(M) · `media`(M) · `storeGroup`(M) · `storeName`(M, `스파오공홈_P_` 접두사 제거) · `uv`(M) · `realCnt`(M) · `realAmt`(M,원) · `bounceRate`(O,%)

### ⑧ storeCorner — 매장코너(코너×컨텐츠) *대용량 → 주 단위 사전집계 권장*
`date`(M) · `media`(M) · `storeGroup`(M) · `store`(O) · `detailNo/detailName`(M) · `cornerNo/cornerName`(M) · `contentType/contentTypeName`(O) · `contentNo/contentName`(M) · `displayOrder`(O) · `clicks`(M) · `impressions`(M) · `ctr`(O) · `buyerCnt/orderCnt/realOrderCnt`(M) · `realAmt/discountAmt/totalBenefit`(M/O,원)

### ⑨ search — 검색 실적(검색어×일자)
`date`(M) · `media`(M) · `keyword`(M) · `success`(O,boolean) · `searchVol`(M) · `uv`(M) · `orderAmt`(O,원) · `orderCnt`(O) · `value`(O,검색어가치)
sigma(M): `{ searchVol, uv, orderAmt, orderCnt, value }`

### ⑩ restock — 재입고 알림내역(품절 수요)
`productNo`(M) · `name`(M, 콜라보 `[IP]` 포함, 끝 `_스타일코드`) · `styleCode`(M) · `optionNo`(O) · `optionName`(M, 예 `(19)Black/S`) · `color/size`(O) · `cnt`(M,대기 고객수) · `vendor`(O) · `status`(O)
추가 메타(M): `totalCnt`(Σcnt) · `productCount` · `skuCount`

### (신규) coupon — 쿠폰 실적(프로모션 효율)
`date`(M) · `promoNo`(M) · `promoName`(M) · `couponType`(O,쿠폰구분) · `promoGroup`(M,프로모션종류그룹) · `registrant`(O,등록자ID) · `issued`(M,발급) · `used`(M,순사용) · `canceled`(O) · `orderAmt`(O,원) · `realAmt`(M,원) · `discountAmt`(M,원,혜택할인) · `burdenMD/burdenMktg/burdenStore/burdenVendor/burdenCS/burdenMembers/burdenEtc`(O,원, 부담주체별)
sigma(M): `{ issued, used, realAmt, discountAmt, burdenMD, burdenMktg }`

### payload 최상위 구조 — ⚠️ 이건 "내부 저장 형태"(우리 Edge Function이 만듦)
아래 주차 래퍼(week_key 등)는 **우리가 저장할 때의 모양**이다. **데이터팀은 이 래퍼를 만들 필요가 없다** — 데이터팀은 1-8①의 "순수 일별 파일"만 드롭하고, 주차 묶음(week_key 산출·payload 조립)은 우리 Edge Function이 한다.
```json
{
  "week_key": "2026-W23", "week_label": "6월 1주",
  "week_start": "2026-06-01", "week_end": "2026-06-07",
  "files_present": ["sales","salesByDate","visit","coupon","restock"],
  "payload": {
    "sales":       { "sigma": {…}, "items": [ … ] },
    "salesByDate": { "sigma": {…}, "items": [ … ] },
    "coupon":      { "sigma": {…}, "items": [ … ] },
    "restock":     { "items": [ … ], "totalCnt": 0, "productCount": 0, "skuCount": 0 }
  }
}
```
**데이터팀이 드롭하는 파일(예)** = 주차 래퍼 없이 그날 데이터셋만:
```
2026-06-22/sales.json   →  { "sigma": {…}, "items": [ /* 6/22 sales 행들 */ ] }
2026-06-22/visit.json   →  { "items": [ /* 6/22 visit 행들 */ ] }
```

## 1-8. 공통 규칙 & 일배치 계약 (★ 역할 분담 명확화)

> **핵심**: "데이터 필드 스키마(1-7)"와 "주차(week)"는 다른 층이다. 필드 스키마는 **날짜(date) 단위**라 일별 데이터에 그대로 맞고, **"주차"는 저장 포장(container)일 뿐**이다. 따라서 아래처럼 책임을 나눈다.

**① 데이터팀 계약 = 순수 "일별" 파일 (week_key 불필요)**
- 데이터팀은 **매일, 데이터셋별로 1-7 표준 스키마 파일**(행에 `date` 포함)만 드롭한다.
- **`week_key`·`week_start/end` 등 주차 정보는 보낼 필요 없음.** 데이터팀은 주차 개념을 몰라도 된다.
- 파일 식별은 **이름 규칙**으로: 예) `2026-06-22/sales.json` (날짜 폴더 + 데이터셋명).

**② 주차 묶기 = 우리 Edge Function 책임 (내부 처리)**
- 우리 Edge Function이 파일의 **날짜로 주차(week_key)를 산출**하고, 그 주의 `weekly_snapshots`에 **누적 upsert**한다.
- 멱등 = **누적-전체교체**: 같은 주의 일별 데이터를 다시 받아도 그 주 payload를 재구성해 통째 교체(재시도·중복 안전).
- 날짜 보유 6종(sales·salesByDate·visit·store·storeCorner·search)은 일자 누적으로 한 주가 완성됨.

**③ 날짜 없는 4종(cart·wishlist·customer·restock) — 일배치 방식 합의 필요**
- 이 4종은 **날짜 컬럼이 없는 기간 집계**라, "일별로 어떻게 줄지" 데이터팀과 합의해야 한다(오류가 아니라 미정 항목):
  - 매일 **"그날까지 누계" 스냅샷**으로 줄지, 아니면 **이 4종만 주 1회**로 줄지.
  - `restock`은 "현재 시점 대기 잔량"이라 **매일 최신값**을 받아 우리가 **최신 1건만** 사용(합산 안 함).
- → 6종은 일별로 깔끔, **이 4종의 산출 방식만 정하면** 끝. (부록 B 질문 6 참조)

## 1-9. 보안 현황 & 적재 보안 (반영됨)
- **대시보드 인증**: 공유 비밀번호 → **Supabase Auth(이메일+비밀번호) 실제 로그인** 적용 완료. 자가가입 차단(관리자 생성 계정만).
- **RLS**: 익명(anon) 차단, **로그인 사용자(authenticated)만** 데이터 접근(전환 SQL 준비/적용 단계). anon 키 노출돼도 권한 없음.
- **적재 보안**: BO는 Storage **업로드 전용** 권한만. **DB 쓰기는 Edge Function 내부의 `service_role`로만**(키는 함수 시크릿, 외부·프론트 금지).
- 전송 HTTPS. (서버 응답 헤더 HSTS/X-Frame-Options 등은 호스팅(noavibe)에서 별도 — 협의 예정. 번들 CSP 메타는 적용됨.)
