# 프로젝트 관리 + 대시보드 확장 설계

**작성일:** 2026-07-28
**대상:** 전사 멀티브랜드 요구사항 관리 웹앱 (`pj/`)
**선행 작업:** 권한 구조 재설계, 로그인/인증 (둘 다 `main`에 병합 완료)

---

## 1. 배경과 목표

현재 시스템은 개별 **요구사항** 단위만 다룬다. 실제 업무에서는 차세대 플랫폼 위에서 하나의 기능을 개발한 뒤 그것을 여러 브랜드로 순차 전개하는 일이 반복된다.

> 예: **빠른배송 시스템 개발** — 스파오에 먼저 적용하고, 이후 미쏘로 확장

지금은 이 "하나의 기능이 브랜드들로 퍼져나가는" 흐름을 표현할 방법이 없다. 스파오의 빠른배송 요구사항과 미쏘의 빠른배송 요구사항은 시스템상 아무 관계가 없는 별개 항목이다.

**목표:** 요구사항보다 상위 단위인 **프로젝트**를 도입해, 하나의 기능이 어느 브랜드까지 전개됐고 각 브랜드에서 얼마나 진행됐는지를 한눈에 관리한다.

### 핵심 관찰

프로젝트는 **브랜드에 속하지 않는다.** 브랜드에 *전개될* 뿐이다. 따라서 프로젝트를 브랜드 하위에 두는 모델(브랜드별로 프로젝트를 복제하고 부모-자식으로 잇는 방식)은 채택하지 않는다. 하나의 기능이 브랜드 수만큼 쪼개져 전사 관점을 잃기 때문이다.

또한 프로젝트는 대부분 **사후에 묶인다.** 요구사항이 먼저 등록되고, 나중에 "이것들이 하나의 기능이구나"라고 인식되는 경우가 많다. 따라서 요구사항의 프로젝트 연결은 **선택사항(nullable)** 이며 언제든 붙이고 뗄 수 있어야 한다.

## 2. 데이터 모델

### 2.1 신규 테이블

```sql
-- 프로젝트: 브랜드에 속하지 않는 전사 단위
create table projects (
  id uuid primary key default gen_random_uuid(),
  name text not null,
  description text,
  owner uuid references team_members(id),
  is_active boolean not null default true,
  created_by uuid references team_members(id),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

-- 전개 현황: 어느 브랜드에 어디까지 갔는지
create table project_brands (
  id uuid primary key default gen_random_uuid(),
  project_id uuid not null references projects(id) on delete cascade,
  brand_id uuid not null references brands(id),
  status text not null default '전개예정'
    check (status in ('전개예정','진행중','적용완료')),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (project_id, brand_id)
);

-- 요구사항 → 프로젝트 (1:N, 선택사항)
alter table requirements
  add column project_id uuid references projects(id) on delete set null;

create index idx_project_brands_project on project_brands (project_id);
create index idx_project_brands_brand on project_brands (brand_id);
create index idx_requirements_project on requirements (project_id);
```

### 2.2 설계 근거

**`projects`에 `brand_id`가 없다.** 프로젝트-브랜드 관계는 전적으로 `project_brands`가 담당한다.

**`project_brands`가 별도 테이블인 이유.** 요구사항의 `brand_id`를 모아 역산하는 방법도 있지만, 그러면 요구사항이 0건인 "로엠 전개예정"을 표현할 수 없다. 계획은 실행보다 먼저 존재하므로 전개 대상을 명시적으로 기록한다.

**삭제 정책이 서로 다른 이유.**
- `project_brands` → `cascade`: 프로젝트가 사라지면 전개 현황은 의미가 없다.
- `requirements.project_id` → `set null`: 프로젝트가 사라져도 요구사항 자체는 유효한 업무 기록이므로 남아야 한다.

**요구사항은 최대 1개 프로젝트에만 속한다.** N:N도 가능하지만 같은 요구사항이 여러 프로젝트의 진척률에 중복 집계되는 문제가 생긴다. 1:N에서 N:N으로의 확장은 나중에도 가능하지만 그 반대는 어렵다.

## 3. 진척률 계산

### 3.1 하이브리드 방식

전개 **상태**는 사람이 지정하고, 진척**률**은 요구사항에서 자동 계산한다.

| 구분 | 출처 | 이유 |
|---|---|---|
| 전개 상태 (예정/진행중/적용완료) | 수동 | 요구사항 0건인 "전개예정"을 표현해야 하고, 실제 오픈 시점은 사람이 판단 |
| 진척률 (완료 N / 전체 M) | 자동 | 상태 갱신을 깜빡해도 요구사항 처리에 따라 계속 움직임 |

두 값이 어긋날 수 있다는 점은 결함이 아니라 **신호로 취급한다.** "적용완료인데 미완료 요구사항 2건 남음"은 확인이 필요한 실제 상황이며, 대시보드에서 명시적으로 노출한다(6절).

### 3.2 계산 규칙

`lib/projectProgress.js`의 순수 함수 `computeProjectProgress()`가 담당한다.

```js
computeProjectProgress({ requirements, projectBrands, brands })
// → { byBrand: [{ brandId, brandName, status, doneCount, totalCount }],
//     overall: { doneCount, totalCount } }
```

`brands`를 함께 받아 `brandName`까지 돌려주는 것은 기존 `computeDashboardStats({ requirements, brands, ... })`와 같은 방식이다. 화면이 이름을 따로 조회하지 않아도 된다.

- **분모에서 중복 요구사항을 제외한다.** `status === '중복'`(`MERGED_STATUS`)인 항목은 병합되어 사라진 것이므로 세지 않는다. 기존 `lib/dashboardStats.js`도 동일한 규칙이라 일관된다.
- **분자는 `status === '완료'`**(`DONE_STATUS`)인 건수다.
- 요구사항이 0건인 브랜드는 `totalCount === 0`이며, 화면에서는 진척률 대신 `—`로 표시한다. 0/0을 0%로 그리면 "시작했는데 진도가 없는 것"처럼 오해된다.

### 3.3 전체 진척률

`overall`은 전개 대상 브랜드 전체의 요구사항을 합산한다. 브랜드별 비율의 평균이 아니다 — 요구사항 12건인 브랜드와 1건인 브랜드를 동등하게 취급하면 왜곡된다.

## 4. 자동 브랜드 추가 규칙

요구사항을 프로젝트에 연결할 때, 그 요구사항의 브랜드가 아직 `project_brands`에 없으면 **`진행중` 상태로 자동 추가한다.**

이 규칙이 없으면 "프로젝트에 속한 요구사항인데 전개 현황에는 안 보이는" 유령 상태가 생긴다. 요구사항이 이미 있다는 것은 그 브랜드에서 작업이 시작됐다는 뜻이므로 초기 상태는 `전개예정`이 아니라 `진행중`이 맞다.

연결 해제 시에는 `project_brands` 행을 자동으로 지우지 **않는다.** 요구사항을 뗐다고 해서 전개 계획 자체가 취소된 것은 아니며, 전개 대상 제거는 1차 관리자의 명시적 행위여야 한다.

## 5. 권한

기존 4단계 등급 체계(`lib/tiers.js`의 `TIER_RANK`)를 그대로 활용한다.

| 동작 | 필요 권한 | 근거 |
|---|---|---|
| 프로젝트 목록/상세 조회 | 로그인한 사용자 | 3차 실무자도 요구사항을 연결하려면 프로젝트를 봐야 함 |
| 프로젝트 생성/수정/보관 | 1차 (전체관리자) | 전사 단위 결정이며, 비슷한 프로젝트 중복 생성을 막음 |
| 전개 대상 브랜드 추가/제거 | 1차 (전체관리자) | 어느 브랜드로 확장할지는 전사 로드맵 판단 |
| 전개 **상태** 변경 | 해당 브랜드 2차 이상 | "우리 브랜드에 적용 완료됐다"는 그 브랜드 팀이 가장 정확히 안다 |
| 요구사항 ↔ 프로젝트 연결/해제 | 해당 브랜드 3차 이상 | 담당자 지정·상태 변경과 같은 수준의 실무 작업 |

전개 상태 변경만 브랜드 단위 권한(`requireBrandAccess(brandId, '2차')`)을 쓰고 나머지 관리 동작은 `requireGlobalAdmin()`을 쓴다. 전체관리자는 `checkBrandAccess`에서 모든 브랜드를 통과하므로 별도 예외 처리가 필요 없다.

## 6. API

모든 라우트는 세션 기반 인가를 사용한다(`lib/auth.js`의 `getSessionMember()`, `lib/permissions.js`). 클라이언트가 보낸 `memberId`는 신뢰하지 않는다.

| 라우트 | 메서드 | 권한 | 설명 |
|---|---|---|---|
| `/api/projects` | GET | 로그인 | 목록. `?brandId=` 로 해당 브랜드 전개 건만 필터, `?includeInactive=true` 로 보관 항목 포함 |
| `/api/projects` | POST | 1차 | 생성 (`name`, `description`, `owner`) |
| `/api/projects/[id]` | GET | 로그인 | 상세 — 프로젝트 정보 + 전개 현황 + 연결된 요구사항 전체(전 브랜드) |
| `/api/projects/[id]` | PATCH | 1차 | 수정 (`name`, `description`, `owner`, `isActive`) — 부분 업데이트 |
| `/api/projects/[id]/brands` | POST | 1차 | 전개 대상 브랜드 추가 (`brandId`) |
| `/api/projects/[id]/brands/[brandId]` | PATCH | 해당 브랜드 2차 | 전개 상태 변경 (`status`) |
| `/api/projects/[id]/brands/[brandId]` | DELETE | 1차 | 전개 대상에서 제거 |
| `/api/requirements/[id]/project` | PATCH | 해당 브랜드 3차 | 프로젝트 연결/해제 (`projectId`, `null`이면 해제) |

### 6.1 세부 동작

**`GET /api/projects`** 는 각 프로젝트에 전개 현황과 진척률을 포함해 반환한다. 목록 화면이 프로젝트마다 추가 요청을 보내지 않도록 한 번에 준다.

**`DELETE /api/projects/[id]/brands/[brandId]`** 는 해당 브랜드에 연결된 요구사항이 남아 있으면 400으로 거절한다. 요구사항이 있는데 전개 대상에서 빼면 4절의 유령 상태가 그대로 생긴다. 에러 메시지로 남은 건수를 알려 사용자가 먼저 연결을 해제하도록 유도한다.

**`PATCH /api/requirements/[id]/project`** 는 연결 시 4절의 자동 브랜드 추가를 함께 수행한다. 두 개의 쓰기가 발생하므로 순서는 **`project_brands` 추가 → `requirements.project_id` 설정**이다. 반대로 하면 전개 현황에 없는 요구사항이 잠시라도 존재하게 된다. 프로젝트 삭제 기능은 이번 범위에 없으므로(보관만 지원) 경합 위험은 낮다.

**프로젝트 삭제는 제공하지 않는다.** `is_active = false`(보관)만 지원한다. 삭제하면 요구사항의 연결 이력이 사라지는데, 되돌릴 방법이 없다.

## 7. 화면

### 7.1 `/projects` — 목록

TopBar에 `프로젝트` 링크를 추가한다.

기본값은 **내 브랜드 중심**이다. 지금 선택한 브랜드에 전개된 프로젝트만 보여주고, 각 행은 그 브랜드 기준 상태와 진척률을 표시한다. `전사 전체` 토글로 모든 프로젝트와 브랜드별 전개 요약을 볼 수 있다.

```
프로젝트                    [내 브랜드] [전사 전체]

프로젝트              스파오 전개상태   진척
빠른배송 시스템 개발   [적용완료]      10/12건
통합 회원 시스템       [진행중]         3/8건
상품 리뷰 개편         [전개예정]         —
```

브랜드 담당자(2·3차)가 사용자의 대다수이고, 앱의 다른 모든 화면이 브랜드 컨텍스트로 동작하므로 기본값을 브랜드에 맞춘다. 전체관리자는 토글을 한 번 눌러야 하지만, 전사 조망이 필요한 상황은 대시보드가 따로 담당한다.

1차 관리자에게만 `+ 새 프로젝트` 버튼을 노출한다.

### 7.2 `/projects/[id]` — 상세

**상단: 전개 현황 카드.** 브랜드별로 상태 배지와 진척바를 나란히 보여준다.

```
빠른배송 시스템 개발            3개 브랜드 · 1개 적용완료
스파오   [적용완료]  ████████░░  10/12건
미쏘     [진행중]    ██░░░░░░░░   1/5건
로엠     [전개예정]  ░░░░░░░░░░     —
```

상태 배지는 권한이 있는 브랜드에 한해 클릭으로 변경 가능하다. 1차 관리자에게는 `+ 전개 브랜드 추가` 버튼과 각 행의 제거 버튼을 노출한다.

**하단: 전 브랜드 통합 칸반.** 기존 `KanbanBoard` 컴포넌트를 재사용하되, 이 프로젝트에 연결된 요구사항을 브랜드 구분 없이 한 보드에 올린다. 카드마다 브랜드명 배지를 달아 어느 브랜드 건인지 구분한다.

드래그로 상태를 바꿀 때는 해당 요구사항의 브랜드에 대한 3차 이상 권한이 필요하다. 권한이 없는 브랜드의 카드는 드래그를 막고 시각적으로 구분한다. 전개 상태 배지와 달리 여기서는 **카드마다 브랜드가 다를 수 있으므로** 카드 단위로 권한을 판정해야 한다.

### 7.3 요구사항 화면

**등록/수정 폼(`RequirementFormDialog`, `RequirementEditForm`)** 에 프로젝트 선택 드롭다운을 추가한다. 선택사항이며 기본값은 미선택이다.

선택지는 **모든 활성 프로젝트**다. 현재 브랜드에 아직 전개되지 않은 프로젝트도 고를 수 있으며, 이 경우 4절의 자동 브랜드 추가 규칙이 동작한다. 다만 현재 브랜드에 이미 전개된 프로젝트를 목록 위쪽에 모아 보여준다 — 대부분의 경우 그중 하나를 고르게 되기 때문이다.

**상세 화면(`RequirementDetail`)** 에 프로젝트 배지를 표시하고, 3차 이상이면 연결/해제할 수 있다. 배지를 누르면 프로젝트 상세로 이동한다.

**목록 화면(`/requirements`)** 의 필터바에 프로젝트 필터를 추가한다.

### 7.4 브랜드 전체 칸반에 대하여

"여러 브랜드 요구사항을 한 보드에서 본다"는 요구는 **프로젝트 상세 안에서만** 충족한다. 기존 `/requirements/board`는 브랜드 한정을 유지한다.

프로젝트라는 맥락 없이 전 브랜드 요구사항을 한 보드에 쏟으면 수백 건이 뒤섞여 오히려 쓸모가 없다. 프로젝트로 범위가 좁혀질 때 비로소 "이 기능이 브랜드별로 어디까지 갔나"라는 의미 있는 뷰가 된다.

---

## 8. 대시보드 확장

`/admin/dashboard`(1차 전용)에 프로젝트 섹션을 추가한다. 기존 브랜드별 통계는 그대로 둔다.

**8.1 요약** — 활성 프로젝트 수, 전개 상태 분포(전개예정/진행중/적용완료 각각 몇 개 브랜드).

**8.2 프로젝트별 전개 진척 테이블** — 프로젝트마다 전개 브랜드 수, 적용완료 브랜드 수, 전체 진척률.

**8.3 불일치 알림** — 전개 상태가 `적용완료`인데 미완료 요구사항이 남은 (프로젝트, 브랜드) 조합을 나열한다.

```
확인 필요
빠른배송 시스템 개발 · 스파오   적용완료인데 미완료 2건
```

이는 데이터 오류가 아니라 실제로 확인이 필요한 상황을 짚어주는 것이다. 오픈 후 후속 작업이 남았거나, 상태를 성급히 바꿨거나, 요구사항 상태 갱신이 누락됐을 수 있다. 세 경우 모두 사람이 봐야 한다.

계산은 `lib/projectProgress.js`에 `findProgressMismatches()`로 함께 둔다. 진척률 계산과 같은 데이터를 쓰므로 한 파일에 있는 것이 자연스럽다.

## 9. 범위 밖

의도적으로 제외한 항목과 그 이유:

- **전개 목표일 / 마일스톤** — 진척도 관리가 자리잡은 뒤에 필요성을 판단한다. 지금 넣으면 관리 대상만 늘고 갱신되지 않을 가능성이 높다.
- **프로젝트 간 의존 관계** — 현재 업무에서 관찰되지 않았다.
- **프로젝트 단위 알림** — `in_app_notifications` 테이블은 있으나 아직 어느 기능도 사용하지 않는다. 알림은 별도 작업으로 다룬다.
- **요구사항 N:N 프로젝트 연결** — 3절 근거 참조. 필요해지면 연결 테이블 추가로 확장 가능하다.
- **프로젝트 삭제** — 6.1절 참조. 보관으로 대체한다.
- **기존 `/requirements/board`의 전 브랜드 토글** — 7.4절 참조.

## 10. 테스트 전략

**순수 함수 (Vitest, TDD):**
- `computeProjectProgress()` — 중복 제외, 0건 브랜드, 전체 합산이 평균이 아님을 각각 검증
- `findProgressMismatches()` — 적용완료 + 미완료 잔여 조합만 골라내는지 검증

**API / 화면:** 이 프로젝트에는 API 통합 테스트 인프라가 없다. 기존 단계들과 동일하게 `npm run lint`와 `npm run build`로 확인하고, 마지막 태스크에서 브라우저로 전체 플로우를 검증한다.

> **주의:** 이 프로젝트의 ESLint 설정에는 import 경로 검사 규칙이 없다. 잘못된 import 경로는 `npm run lint`를 통과하고 `npm run build`에서만 드러난다. import를 추가하는 태스크는 반드시 build까지 돌린다.

**마이그레이션:** 자동 러너가 없으므로 `supabase/migrations/0006_projects.sql`을 Supabase SQL Editor에 직접 실행한다.
