# SPAO 키즈 실적 자동화 대시보드 — 설계

**작성일**: 2026-07-10 · **기준**: `★스파오키즈_주문실적판_2607(1).xlsb`(브랜드 키즈팀 수기 실적관리판) 구조 분석 + 기존 `spao-dashboard-v3`(SPAO 성인) 플랫폼

## 0. 배경 — 원본 워크북 구조

키즈팀이 매일 수기로 갱신하는 `.xlsb`는 서로 다른 4갈래 원천 + 화면용 집계 시트로 구성되어 있다.

| 원천 시트 | 성격 |
|---|---|
| `공홈 당일` | 자사몰(스파오공홈) 주문상세 — 수기 다운로드로 보이는 주문 단위 로우데이터 |
| `네이버 당일` | 네이버 스마트스토어 주문/배송 상세 |
| `이랜드몰 당일/전년` | 통합몰(백화점 입점매장 KIDIKIDI·NC강서 등 포함) 주문상세 |
| `일자별 로우`/`일자별 로우(중간)`/`Sheet1` | "매출상세분석" — 전사 ERP/BI 큐브 리포트로 보임(오프라인 매장 포함 전 채널) |
| `INDEX` | 52주 캘린더 헬퍼(순수 계산용, 소스 불필요) |
| `목표` | 비어있음 — 수기 입력 시트로 추정 |
| `①당일`/`②당월`/`③연계획` | 위 원천을 SUMIFS/VLOOKUP으로 집계하는 화면 시트 |

기존 `spao-dashboard-v3`는 SPAO 성인 자사몰의 N.E.E.D BI 수집기(14종 엔드포인트)를 Supabase Edge Function(`super-action`)으로 자동 적재하는 파이프라인을 이미 구축했고, `weekKey.js`(주차 계산)·`storage.js`(gzip 압축 저장)·Supabase Auth 인증·WoW 비교 로직이 검증되어 있다. `MULTI_BRAND.md`는 이 플랫폼을 "Brand Config 레이어"로 분리해 멀티브랜드로 확장하는 설계도 이미 제시한 바 있다.

## 1. 확인된 사실 (사용자 확인 완료)

- **자사몰(공홈)**: 성인·키즈가 **같은 사이트/관리자**를 공유하며 상품만 다르다. 스타일코드의 성별코드(8번째 문자)가 `K`인 행이 키즈 상품이다. N.E.E.D가 이미 이 자사몰 데이터를 매일 자동 수집 중이므로, **키즈 몫은 별도 연동 없이 필터링만으로 확보 가능**하다.
- **네이버**: 성인과 **별도 셀러 계정**을 운영한다. 자동화하려면 키즈 계정용 네이버 커머스 API 자격증명이 별도로 필요하다.
- **이랜드몰(통합몰)/매출상세분석(ERP)**: 자동 추출·API 가능 여부가 **미확인** 상태다. 확인될 때까지는 파일 업로드로 임시 다리를 놓는다.
- **목표/연계획**: 이번 스코프에서는 제외한다(향후 별도 검토).

## 2. 전체 구조 — 2개 트랙

이 프로젝트는 성격이 다른 두 산출물로 나눈다.

### 트랙 1 — 기존 v3 대시보드에 "키즈" 세분화 (완료)

**목적**: 이미 자동으로 흘러들어오는 성인 자사몰 데이터에서, 새 연동 없이 키즈 몫만 걸러 보여주는 가장 값싼 win.

**구조**: L1~L4와 나란한 **새 최상위 탭("키즈")**을 신설한다. L1~L4 컴포넌트 내부에 성인/키즈 토글을 끼워 넣지 않는다 — 그러면 기존 4개 컴포넌트를 전부 건드려야 해서 회귀 위험이 커진다. 대신 컴포넌트는 이미 `items` 배열만 받아 비율을 재계산하는 구조이므로, **같은 컴포넌트에 "키즈만 걸러낸 payload"를 꽂아주는 방식**을 쓴다.

- 신규: `src/utils/kidsFilter.js` — `filterPayloadByGender(payload, 'K')`
  - `sales`/`cart`/`wishlist`/`restock`: styleCode가 있는 상품 단위 데이터셋 → 필터링 후 `sigma` 재계산
  - `salesByDate`/`visit`/`store`/`storeCorner`/`search`/`coupon`/`customer`: styleCode가 없어 상품 단위로 쪼갤 근거가 없는 데이터셋 → **null 처리**(성인+키즈 합산값을 키즈 라벨로 잘못 보여주는 것을 방지)
- 신규: `App.jsx`에 `kids` 탭 추가. `kidsDerived`를 별도 `useMemo`로 계산해 기존 `derived`(성인)와 독립적으로 유지. `L1_HealthCheck`(`salesByDateMetrics`/`searchMetrics`는 null로 전달)와 `L2_ProductAnalysis`를 그대로 재사용하고, 상단에 "일부 지표는 상품 단위로 집계할 수 없어 비어 있다"는 안내 배너를 추가.
- 기존 L1~L4 컴포넌트·성인 쪽 로직은 **한 줄도 변경하지 않음**.
- 신규 백엔드/스키마 불필요 — 이미 흐르는 N.E.E.D 데이터를 재사용.

**검증**: `filterPayloadByGender`에 대한 vitest 단위 테스트 작성(4종 케이스: 성별 필터링, sigma 재계산, null 처리, null-safety) — 전체 기존 테스트(70개)와 함께 통과 확인. 로컬 dev 서버(`spao-dashboard-v3`, :3458) 기동 확인 — 콘솔 에러 없음. 실제 로그인 후 화면 확인은 Supabase Auth 계정이 필요해 사용자가 직접 진행.

### 트랙 2 — 키즈 전용 대시보드 (신규, 후속 작업)

**목적**: 자사몰·이랜드몰·네이버 3개 온라인 채널의 "당일/당월" 실적을 하나의 화면으로 통합해, 지금의 수기 엑셀 실적판을 대체한다.

**스코프**: 3개 온라인 채널의 당일/당월 실적만. ERP(매출상세분석)·오프라인 매장(백화점/직영점)·연계획/목표는 이번 스코프 밖(향후 재검토).

**배포**: 기존 `spao-dashboard-v3`와 같은 Supabase 프로젝트(인증·비용 재사용)에 **새 테이블**을 추가하는 방식. 기존 `weekly_snapshots`(gzip jsonb, 주 1회 수기 업로드에 최적화된 저장 방식)는 재사용하지 않는다 — 트랙 2는 API로 매일 들어오는 구조라 **일자×채널 단위의 평범한 관계형 테이블**이 더 자연스럽다.

**공통 스키마(잠정 — 아래 3장 참고)**:
```
kidsChannelDaily (일자 × 채널)
  date(M) · channel(M, '자사몰'|'이랜드몰'|'네이버') · orderCnt(M) · orderAmt(M,원)
  · realOrderCnt(M) · realAmt(M,원) · cancelAmt(M,원) · discountAmt(O,원)

kidsProductDaily (일자 × 채널 × 상품, 선택 — 상품 랭킹용)
  date(M) · channel(M) · styleCode(M) · name(M) · qty(M) · realAmt(M,원)
```

**채널별 정규화 어댑터**:

| 채널 | 원본 형태 | 어댑터 |
|---|---|---|
| 자사몰 | N.E.E.D가 이미 수집한 `salesDaily`/`itemAggrList`(집계됨) | 트랙1과 동일한 K-필터만 적용 → 공통 스키마로 매핑(신규 파싱 불필요) |
| 네이버 | 네이버 커머스 API 주문 목록(로우) | 신규 Edge Function이 매일 pull → 일자별 집계 → 매핑 |
| 이랜드몰 | 현재 사람이 다운로드하는 주문상세 엑셀(로우) | 임시: 업로드 UI로 파일 받아 서버에서 집계 → 매핑. 자동 추출 확인되면 이 어댑터만 교체 |

상품명 끝의 `_스타일코드` 추출은 기존 `styleCodeParser.js`를 재사용한다.

**화면 구성(1차)**:
- 당일 스코어보드: 채널별 TTL 매출·목표달성율·전년 동요 대비 성장률(카드형)
- 당월 누적: 올해 누적 vs 작년(동요/동일) vs 누적목표(채널별 표)
- 일별 추이: 최근 N일 채널별 매출 추이 + 전년 대비 성장률
- 목표 숫자만 간단 입력 폼으로 받음(연계획 시트 전체 이식 아님)
- **향후 확장 전제**: 위 화면·범위는 1차 버전이며, 사용 중 피드백에 따라 추가/수정될 것으로 예상한다.

## 3. 리스크 & 미확정 사항

- **스키마는 잠정이다.** 네이버 커머스 API 실제 응답과 이랜드몰 엑셀의 정확한 필드명·취소/환불 표현 방식은 아직 검증되지 않았다. 착수 전 **Phase 0(검증)**에서 실제 샘플을 확보해 매핑표와 스키마 필드를 확정한다.
- 이랜드몰/ERP 자동화 가능 여부 미확인 — 확인될 때까지 파일 업로드가 임시 다리 역할을 한다.
